# qa — 그 사람이 되어 끝까지 써 보고, 재어 보고 말한다

## 0. 이 스킬이 하는 것

만든 사람 눈에는 안 보이는 불편을, **쓰는 사람이 되어** 찾는다. 코드가 돌아가느냐가 아니라
"사장이 아침에 로그인해서 30초 안에 오늘 할 일을 아느냐", "비밀번호를 잊으면 어떻게 되느냐",
"잘못 올린 서류를 지울 수 있느냐"를 본다. 2026-09-05 weddingCORE 예행연습에서 비밀번호 찾기 없음,
고객 정보 수정 불가, 서류 삭제 불가, 규칙과 화면의 값이 달라 항상 거부되는 버튼 등 22건이
한 번에 나왔다. 대표 판단은 "전부 타당하다".

세 단계다. **1단계 찾기**(보고만, 고치지 않음 · §2) → 사용자 확인 → **2단계 고치기 + 백그라운드 점검 N개**(§3)
→ **3단계 지키기**(§8·§9). 3단계를 빼면 다음 달에 같은 것을 또 찾는다.

찾을 때는 **두 눈을 함께 쓴다.** 코드를 끝까지 추적하는 눈(§2-2)과, 화면을 실제로 보는
눈(§2-3·§2-4 — 제미나이 시각 QA)이다. 하나만 쓰면 절반을 놓친다. 서비스가 이미 돌고 있으면 **세 번째 눈**이
있다. 실사용 기록(§9)이다. 사람이 어느 걸음에서 실제로 멈췄는지는 코드도 그림도 말해 주지 않는다.

**전체 흐름 한 줄.** 누구인가(§1) → 지도(§2-1) → 코드 추적(§2-2) → 눈으로 보기(§2-3·§2-4) → 재기(§2-5)
→ 눌러 보기(§2-6) → 표로 보고하고 멈춤(§2-7) → 승인 뒤 고치기(§3) → 심각도로 줄 세우기(§4)
→ 점검자 N개(§5) → 지켜보는 장치 세우기(§8) → 실사용 기록으로 계속 듣기(§9).
금지 목록은 §6, 점수 루프는 §7에 따로 있다.

## 0-1. QA는 세 갈래다 — 어느 것을 부른 것인지 먼저 가린다

| 무엇을 묻는가 | 어디서 하는가 | 판정 |
|---|---|---|
| **쓰는 사람이 막히는가** (없는 기능, 막다른 안내, 어려운 말, 잃는 데이터) | **이 스킬.** 사람이 되어 여정을 따라가며 코드까지 추적 | 막힘·위험·답답·말 (§4) |
| **화면이 이상하게 보이는가** (가독성, 정렬, 여백, 잘림) | 이 스킬 §2-4. 화면을 찍어 제미나이에게 넘긴다 | P0~P2 |
| **기술 규격이 맞는가** (robots·sitemap·canonical·메타·JSON-LD·헤더) | **`site-qa` 스킬.** 빌드 산출물에 약 70개 결정적 검사 | PASS·WARN·FAIL |

- 사용자가 그냥 "QA 돌려"라고 하면, **공개 사이트를 배포하기 전이면 `site-qa`부터** 돌려 REQUIRED FAIL을 0으로
  만들고, 그 다음에 이 스킬로 사람 QA를 한다. 기술 결함은 결정적으로 잡히고 사람 문제는 그렇지 않다.
- **배포 전 기준 순서(이 스킬 전체가 이 순서를 따른다).**
  `typecheck → build → site-qa(FAIL 0) → 권한 테스트 → 스모크 테스트 → 배포 → 화면 확인(§2-4) → 감시가 살았는지 확인(§8)`.
  §3-5의 검증도 §8의 배포 전 칸도 같은 순서다. 권한·스모크가 없는 프로젝트면 §8을 보고 만들거나, **없다고 보고한다.**
- **점수를 목표로 삼지 않는다.** `site-qa`에도 총점이 없다. 결함 목록과 그 근거가 산출물이다.
  점수로 루프를 돌리는 경우는 영상·디자인 같은 산출물을 다듬을 때뿐이며 규칙은 §7에 따로 적었다.
- **이 세 갈래는 모두 「한 번 훑는 일」이다.** 서비스가 돌기 시작한 뒤에 질을 지키는 장치는 §8,
  실사용자가 어디서 막히는지 아는 법은 §9에 있다. 배포 전 점검만 하고 끝내지 않는다.

## 1. 누구인가부터 정한다

- 사용자가 말한 사람을 그대로 쓴다. 안 정했으면 하나 골라 밝히고 진행한다(묻지 않고 막히지 않는다).
- 그 사람을 한 문단으로 그린다. 예(결혼정보회사 사장): 개발자가 아니다. 휴대폰을 더 많이 쓴다.
  하루에 손님 전화 몇 통, 서류 준비, 관공서 대응. 50대 이상이면 작은 글씨를 못 읽고 작은 버튼을
  잘못 누른다. **화면에 뜬 글자 그대로 읽는다.** 개발 용어·법률 한자어를 모른다.
- 그 사람의 여정을 적는다. 처음 가입 → 매일 하는 일 → 돈 내는 일 → 실수했을 때 → 그만둘 때.
- **신고할 수 있는 사람인지 적는다.** 고장이 나면 전화하는 사람인가, 조용히 포기하는 사람인가.
  포기하는 쪽(고령자·환자·불안한 의뢰인)이면 §9의 장치가 없으면 우리는 영원히 모른다.

## 2. 1단계 · 찾기 (보고만 한다)

### 2-1. 지도 그리기
- 라우트·페이지·메뉴를 뽑는다(`routes.tsx`, `Sidebar`, 페이지 파일 크기).
- 그 사람이 지나가는 화면을 여정 순서로 나열한다. 안 지나가는 화면은 뒤로 미룬다.

### 2-2. 화면마다 코드로 끝까지 추적
- 페이지 → 훅 → 서버 함수 → **저장 규칙(firestore.rules·storage.rules)** 까지 따라간다.
  규칙에서 실제 버그가 나온다. 예: 화면의 상품 ID(`pack_110`)와 규칙의 허용 목록(`pack_50`)이
  달라 "계좌이체 신청" 버튼이 항상 거부. Storage `allow write`에 `request.resource.size` 조건이
  있으면 삭제 요청은 평가가 실패해 삭제가 안 된다.
  **규칙에서 한 건이라도 나오면 그 자리가 §8 권한 테스트를 만들 자리다** — 같은 실수를 다음에는 사람이 아니라 검사가 잡는다.
- 화면에 실제로 뜨는 글자와 버튼을 눌렀을 때 일어나는 일을 본다. 다음을 반드시 확인한다.
  - **없는 것**: 수정·삭제·되돌리기·비밀번호 찾기·검색·정렬·필터·읽음 처리·확인 단계.
  - **막다른 곳**: "관리자에게 문의하세요", 링크 없는 안내, 누르면 아무 일도 없는 카드(예: `?filter=overdue`를
    보내는데 받는 쪽이 안 읽음), 빈 화면에 다음 행동 없음.
  - **거짓 정보**: 고정 상수를 실시간 값처럼 보여 주는 것(예: 모든 업체가 똑같이 "준비도 40점").
  - **말**: 영어 소제목, 개발 용어, 법전 말, 내부 ID 노출, 영어 오류 코드 그대로, 겁 주는 이름("법적 위반").
  - **위험**: 확인 없는 삭제, 조용히 실패하는 try/catch, 필수 항목이 현장에서 모르는 값.
  - **휴대폰**: 고정 다이얼로그·서랍의 폭, 하단 메뉴 개수, 10~11px 글자, 44px 미만 버튼.
- 주장마다 `파일:줄`을 잡아 둔다. 추측은 추측이라고 쓴다. 코드에 없는 기능을 있다고 쓰지 않는다.
- 서비스가 이미 돌고 있으면 **「없는 것·막다른 곳」을 기록과 견준다**(§9). 코드에 있는 버튼을
  실제로는 아무도 누르지 않는 일이 있고, 그건 없는 것이 아니라 **안 보이는 것**이다.

### 2-3. 눈으로 본다 — 코드만 읽으면 보이는 문제를 못 잡는다

**이 단계를 건너뛰지 마라.** 2026-09-12 퇴사히어로 예행연습은 149건을 찾고도
**화면을 한 번도 보지 않았다.** 코드 추적은 "무엇이 안 되는가"를 잡고,
눈은 "무엇이 안 보이는가"를 잡는다. 둘은 겹치지 않는다.

- 공개 화면은 배포본 주소를 그대로 찍는다(개발 서버를 띄울 필요가 없다).
- **비밀번호를 대신 입력하지 않는다.** 로그인 뒤 화면은 코드로 검토하고 그렇게 했다고 밝힌다.
  진짜 눌러 보는 검증이 필요하면 사용자에게 로그인만 해 달라고 한다.
- 사람이 직접 볼 필요는 없다. **제미나이에게 눈을 맡긴다(§2-4).**

### 2-4. 시각 점검 — 제미나이 (검증된 절차, 2026-09-12 실호출)

내가 만든 화면을 내가 보면 익숙해서 안 보인다. **찍어서 다른 눈에 넘긴다.**

**① 찍는다.** 전역 `to-png`는 PowerShell 함수라 bash에서는 스크립트를 직접 부른다.

```bash
T=/c/Users/jeonw/tools/headless-tools/to-png.mjs
node $T "https://example.com/"  shots/home-desktop.png --width 1440 --height 900 --full-page --wait-ms 8000
node $T "https://example.com/"  shots/home-mobile.png  --width 390  --height 844 --full-page --wait-ms 8000
```

- **데스크톱과 모바일을 반드시 둘 다** 찍는다. 데스크톱만 괜찮은 화면은 완성이 아니다.
- **`--wait-ms`는 8000부터 시작한다.** 챗봇 위젯·등장 애니메이션·SPA 번들이 자리를 잡을 시간이다.
  2500은 짧다 — 2026-09-12 학점나비 교사 예행연습에서 **2500으로 찍어 오판 두 건**이 났다.
  하나는 로딩 스피너만 찍혀 "대시보드가 안 뜬다"가 됐고, 하나는 페이드인 중간이 찍혀
  제미나이가 **"본문 대비가 매우 낮아 읽기 어렵다"를 가장 심각한 문제로 올렸다.** 8초에 다시 찍으니 둘 다 정상이었다.
  그대로 고쳤으면 멀쩡한 색을 바꾸고 없는 버그를 쫓았을 것이다.

**⚠ 짧게·길게 두 번 찍어 견준다 — 이 절차를 건너뛰지 마라.**

```bash
node $T "$URL" shots/x-2s.png --width 390 --height 844 --wait-ms 2000
node $T "$URL" shots/x-8s.png --width 390 --height 844 --wait-ms 8000
```

두 장이 **다르면 화면 문제가 아니라 촬영 문제**다. 제미나이에는 **긴 쪽만** 넘긴다.
다만 그 차이 자체는 버리지 말고 **「느리다」는 별개 발견으로 남긴다** — 손님은 2초에 보는 화면으로 판단하기 때문이다.
차이가 큰 화면(빈 화면 → 정상)은 대개 **프리렌더가 안 된 경로**다. 라우트 목록에 있는지 확인해 볼 것.

색·대비·가독성 지적이 올라오면 **먼저 이 함정부터 의심한다.** 페이드인이 그대로 그 증상을 만든다.
- **손님 여정의 화면을 전부** 찍는다. 홈·랜딩·도구·결제·완료·마이페이지.
  그리고 **빈 상태와 오류 상태**도 찍는다 — 그쪽이 대개 더 나쁘다.

**② 넘긴다.**

```bash
set -a && . /c/Users/jeonw/.gemini/.env && set +a     # GEMINI_API_KEY
export GEMINI_CLI_TRUST_WORKSPACE=true                 # 없으면 실행 자체가 거부된다
gemini -p "/visual:qa <서비스와 손님 한 줄>. 데스크톱 @shots/a-desktop.png · 모바일 @shots/a-mobile.png"   --approval-mode plan
```

- 구현 전 방향을 잡을 때는 `/visual:direction`이 따로 있다. QA는 `/visual:qa`다.
- `--approval-mode plan`으로 읽기 전용으로 묶는다. 제미나이가 파일을 고치게 두지 않는다.

**③ 함정 (전부 실제로 막혔던 것)**

| 증상 | 원인·대응 |
|---|---|
| `GEMINI_API_KEY를 지정하라` | 키는 `~/.gemini/.env`에 있다. 위처럼 불러 온다 |
| `not running in a trusted directory` | `GEMINI_CLI_TRUST_WORKSPACE=true` 를 넣는다 |
| `Path not in workspace: .../visual-director/SKILL.md` | 스킬 파일이 작업 폴더 밖이라 못 읽는다. **무시해도 된다** — 출력 계약이 `~/.gemini/commands/visual/qa.toml` 안에 이미 들어 있어 형식은 그대로 나온다 |
| `Ripgrep is not available` / IDE 연결 실패 | 경고일 뿐 결과에 영향 없다 |
| 제미나이가 **「대비가 낮다·글씨가 흐리다·로딩만 보인다」**를 최상위로 올림 | **촬영이 이른 것**을 먼저 의심한다. 8초로 다시 찍어 견주고, 같으면 진짜 문제·다르면 기각하고 「느리다」로 옮긴다 |

**④ 판정**

`VISUAL PASS` 한 줄이거나, 최대 5줄로 `PRIORITY | AREA | VISUAL PROBLEM | WHY IT MATTERS | RECOMMENDED CHANGE`가 온다.
**P0부터 고친다.** 실제 산출 예(퇴사히어로 홈).

```
P0 | Hero | 모바일 히어로 영역 텍스트 가독성 저하 | 불안한 사용자가 정보를 즉시 파악하기 어려움 | 배경 이미지 어둡게 처리 또는 텍스트 그림자 추가
P1 | Layout | 데스크톱 내비게이션 바 메뉴 간격 불균형 | 브랜드의 전문성과 신뢰도 하락 | 각 메뉴 아이템 간 여백을 일정하게 통일
```

**⑤ 지킬 것**

- **스크린샷 없이 판정하게 하지 않는다.** 소스를 주면 코드로 추측해 버린다. 그림만 준다.
- 시각 QA 결과도 **코드로 다시 확인한 뒤** 체크리스트에 옮긴다(§3-4와 같다).
  "정렬이 어긋나 보인다"가 실제 CSS 문제인지 스크린샷 렌더 차이인지는 봐야 안다.
- **기각한 지적은 기각했다고 보고한다.** 몇 건을 왜 버렸는지 적지 않으면, 다음 사람이 같은 오판을
  다시 주워 고치려 든다. 2026-09-12에 「대비 낮음」 1건을 기각하고 그 자리에 「애니메이션이 느리다」를 남겼다.
- **촬영은 내가 한다.** 점검 에이전트에게는 여전히 브라우저·도구를 주지 않는다(§3-2).
- 고친 뒤 **다시 찍어 다시 넘긴다.** 눈으로 고친 것은 눈으로 확인한다.
- 찍은 장을 버리지 않는다. 배포 전후로 같은 화면을 견주는 **시각 회귀(§8)의 기준 사진**이 된다.

### 2-5. 재고 나서 말한다 — 눈으로 본 것을 진단으로 올리기 전에

**2026-09-12 콕출근에서 "섹션마다 정렬이 어긋난다"고 진단했다. 재어 보니 아홉 섹션이 모두
`left=230, width=980`으로 한 픽셀도 어긋나지 않았다.** 눈에 그렇게 보인 이유는 정렬이 아니라
오른쪽이 비어 있어서였다. 재지 않고 고치기 시작했으면 멀쩡한 CSS를 세 곳 건드렸을 것이다.

- **숫자로 말할 수 있는 주장은 숫자를 먼저 잡는다.** 정렬·폭·높이·간격·개수·시간은 전부 잴 수 있다.
  브라우저 콘솔이나 `to-png.mjs` 대신 짧은 puppeteer 스크립트로 `getBoundingClientRect()`를 찍는다.
  잰 값은 보고문에 함께 쓴다("아홉 섹션 모두 left=230 · 본문 전체 높이 12,027px").
- **고치고 나서 다시 잰다.** 2026-09-12에 두 단 배치로 오른쪽 빈 공간은 없앴지만 전체 높이는 4%밖에
  줄지 않았다. 재지 않았으면 "훨씬 짧아졌다"고 보고했을 것이다.
- **원인을 두 개 이상 의심할 때는 갈라서 잰다.** 배경음악의 「치치직」을 음악 탓으로 보고 하이햇을
  줄였더니 6kHz 이상이 0.2dB만 내려갔다. 음악과 효과음을 **따로 만들어 따로 재니** 음악 −32.0dB,
  효과음 −23.1dB로 범인이 갈렸다. 짐작으로 한 곳을 고치고 "조금 나아졌다"고 하지 않는다.
- **앞서 내가 한 진단이 틀렸으면 표로 철회한다.** 「무엇을 주장했는가 · 실제로 잰 값 · 그래서 무엇이
  바뀌는가」 세 칸이면 된다. 조용히 말을 바꾸면 다음 세션이 틀린 진단을 다시 주워 고치려 든다.

### 2-6. 직접 눌러 볼 때 지킬 것 (브라우저 자동화)

로그인 뒤 화면을 눌러 봐야 하거나, 남의 사이트 양식을 채워야 할 때다. §2-3의 원칙(비밀번호를 대신
입력하지 않는다)은 그대로 지킨다. 그 위에 **남의 화면 상태를 망가뜨리지 않기 위한** 규칙이다.

- **살아 있는 화면에 시험 글자를 넣지 않는다.** 2026-09-12에 서식이 되는지 보려고 편집기에 시험
  문장을 붙여 넣었고, 그 문장이 남아 실제 원고가 그 안에 끼어 들어갔다. 서식 확인은 빈 칸이나
  내가 만든 화면에서 한다. 이미 넣었으면 **새로 고쳐 되돌리고** 그 사실을 보고한다.
- **같은 조작이 두세 번 실패하면 멈춘다.** 창 크기가 575px로 줄어 스크린샷이 계속 시간 초과된
  일이 있었다. `resize_window`는 성공이라 답하는데 `innerWidth`는 그대로였다. 세 번에서 멈추고
  「무엇을 시도했고 · 무엇이 돌아왔고 · 사용자가 무엇을 해 주면 되는지」를 표로 보고한다.
  더 시도할수록 화면 상태만 나빠진다.
- **떠나기 전 경고가 붙은 화면에서는 `navigate`가 막힌다.** 저장 안 된 입력이 있는 양식은
  브라우저 대화상자를 띄우고, 대화상자가 뜨면 확장은 명령을 더 받지 못한다. 새로 고침·이동은
  사용자에게 부탁한다.
- **부자 편집기(TipTap·ProseMirror·Quill)는 DOM을 고쳐도 원래 내용으로 되돌린다.** 방법은 하나다.
  편집기 안에 `Range`를 잡아 선택 → **0.2초 기다림** → `ClipboardEvent('paste')`를 보낸다.
  기다림을 빼면 선택이 반영되기 전에 붙여넣기가 나가 실패한다. `execCommand('selectAll')`,
  가짜 `ctrl+a`, React 인스턴스 찾기는 모두 듣지 않았다(2026-09-12 modoo.or.kr에서 확인).
- **파일 올리기는 한 번에 하나씩.** 여러 개를 한 번에 넘기면 첫 개만 올라간다. 그리고 올릴 파일은
  세션이 읽을 수 있는 폴더(프로젝트 안)에 **아스키 이름**으로 복사해 둔다.

### 2-7. 보고 형식
- 세 묶음: **당장 업무가 막히는 것 / 매일 쓰다 보면 답답한 것 / 말이 어렵거나 불안하게 하는 것.**
  데이터를 잃는 것은 첫 묶음에 넣는다. **시각 점검(§2-4) 결과는 네 번째 묶음
  「화면이 이상하게 보이는 것」으로 따로 묶는다** — 원인이 코드가 아니라 디자인이라 고치는 사람이 다르다.
- 항목마다 굵은 한 줄 + 사장이 겪는 현상 한두 문장. 파일 이름·코드는 쓰지 않는다(근거는 따로 갖고 있다).
- **묶음마다 표로 먼저 보여 준다**(무엇이 · 누가 겪는다 · 얼마나 급하다). 줄글로 길게 설명하면
  사장이 무엇을 결정해야 하는지 못 찾는다. 표 아래에 굵은 한 줄씩 풀어 쓴다.
- 돌고 있는 서비스면 **항목마다 숫자를 붙인다**(§9). "불편해 보인다"와 "어제 34명 중 9명이 이
  걸음에서 멈췄다"는 사장에게 전혀 다른 글이다.
- 보고 끝에 **지켜보는 장치 표**(§8)를 한 번 붙인다. 있는 것·없는 것 두 칸이면 된다.
  결함만 보고하면 "왜 우리가 몰랐나"에 답하지 못한다.
- 마지막에 "먼저 고칠 순서"를 없으면 서비스를 못 쓰는 것부터 적는다.
- **여기서 멈춘다.** 고치지 않는다. 사용자가 판단한다.

## 3. 2단계 · 고치기 + 백그라운드 점검 N개

사용자가 "타당하다", "수정 시작해"라고 하면 시작한다.

### 3-1. 문서 먼저 (전역 §7)
- `docs/checklist-ux.md`: 1차 발견을 세 묶음 그대로 체크박스로. "2차 발견" 절을 비워 둔다.
- `docs/context-notes.md`: 지시 원문, 진행 방식, 규칙에서 확인한 것을 새 절로.
- 체크리스트에 **「지킬 장치」 절을 비워 둔다**(§8). 고치는 일이 끝나면 거기가 다음 할 일이다.

### 3-2. 백그라운드 점검을 먼저 띄운다
- 영역을 N개(기본 15)로 나눈다. 예: 가입·로그인 / 대시보드·알림·레이아웃 / 목록·등록 / 상세·타임라인 /
  서류 / 신상정보 / 접수 / 매칭 / 비자 / 자동화·결제 / 마케팅·위젯·손님 화면 / 업체정보·규제 /
  공개 콘텐츠·챗봇 / 휴대폰·접근성·상태 표시(전 화면) / 문구·용어·오류 전수(전 화면) /
  **지켜보는 장치·기록**(§5 마지막 문단의 관점 여섯 개를 준다).
- `Agent`(general-purpose)를 **한 메시지에 N개** 띄운다. 프롬프트 뼈대는 아래 §5. 반드시 넣을 것:
  같은 사람 묘사, 담당 영역과 "반드시 읽을 파일", 점검 관점 질문 10개쯤, 근거 규칙,
  **금지(수정·커밋·브라우저·빌드·실데이터)**, **이미 찾은 목록(중복 금지)**, 산출물 경로
  `docs/ux-audit/NN-slug.md`와 형식, 최종 답변 형식.
- 브라우저 금지 이유: 점검자 N개가 창 하나를 나눠 쓰면 서로 밟는다.

### 3-3. 그 사이에 고친다
- 순서: **없으면 서비스를 계속 못 쓰는 것**(비밀번호 찾기, 수정·정리, 삭제, 단계 변경, 항상 실패하는
  버튼) → 매일 돌아가는 것 → 말.
- **고치기 전에 재현 검사를 먼저 만든다**(§8 「버그 하나에 검사 하나」). 그 검사가 빨개지는 것을
  보고 나서 고친다. 검사로 만들 수 없는 것(디자인·문구)은 §2-4의 사진으로 대신한다.
- 규칙 수정이 필요한 것은 규칙과 화면을 같은 커밋에. 규칙 배포(`deploy:rules`)를 잊지 않는다.
- 한 논리 단위마다 커밋(전역 §9). 문구 정리는 한 커밋으로 묶는다.
- 고칠 때 **전역 §11(한국어 출력 규칙)** 을 같이 적용한다. 링크 없는 안내를 만들지 않는다.

### 3-4. 점검 결과가 오면
- 산출물을 읽고 **각 주장을 코드로 다시 확인**한 뒤 체크리스트 "2차 발견"에 옮긴다. 점검자가 틀린 것은
  "기각 · 이유"로 남긴다. 중복은 합친다.
- 심각도 순으로 이어서 고친다. 범위가 큰 것(예: 매칭 상대방 설계)은 "뒤로"로 표시하고 이유를 적는다.
- 결과가 수백 건이면 **「막힘」 전부와 고친 것만** 옮기고, 「위험」은 다음에 먼저 볼 것 10여 건만 요약한다.
  옮긴 항목마다 **확인/미확인**을 붙인다. 코드로 다시 보지 않은 주장은 미확인이다(2026-09-05 밤, 300건).

### 3-5. 검증과 보고
- **§0-1의 기준 순서 그대로** 돌린다. `typecheck` → `build` → 공개 사이트면 `site-qa`(FAIL 0) →
  권한·스모크 → 함수 바꿨으면 함수 빌드 → 배포(프로젝트 노트의 배포 절차).
- 마지막 보고: 고친 것 / 못 고친 것과 이유 / 사용자가 직접 눌러 볼 것 세 가지.
- 배포 뒤 **감시가 살아 있는지와 건강 지표 한 줄**을 함께 보고한다(§8). 고친 일은 배포로 끝나지
  않고 그 숫자가 움직일 때 끝난다.

### 3-6. 중단됐다가 이어서 할 때
- `git status`와 `docs/CLAUDE_HANDOFF_*.md`를 먼저 본다. **다른 도구가 남긴 미커밋 변경**이 있을 수 있다.
  typecheck·build를 돌려 통과하면 논리 단위로 먼저 커밋(본문에 "다른 도구 세션의 작업")하고 그 위에서 고친다. 되돌리지 않는다.
- 앞 세션이 규칙을 고치고 **배포하지 않은 채** 중단됐을 수 있다. 체크리스트 「검증」 절이 비어 있으면 규칙부터 배포한다.
- 점검 보고서가 N개 중 몇 개 비어 있으면(예: 15번 문구 전수) 그 영역은 직접 전수 조사한다.

## 4. 판단 기준 (심각도)

| 심각도 | 뜻 | 예 |
|---|---|---|
| 막힘 | 업무를 못 한다 | 비밀번호 찾기 없음, 수정 불가, 항상 거부되는 버튼 |
| 위험 | 실수로 잃거나 잘못 판단한다 | 확인 없는 삭제, 조용한 실패, 고정값을 실시간처럼 |
| 답답 | 되긴 하는데 돌아간다 | 필터 안 되는 카드, 두 번 눌러야 하는 흐름, 필수 항목 과다 |
| 말 | 문구·용어·이름 | 영어 소제목, 개발 용어, 내부 ID, 영어 오류 |

**기록과 감시에서 나온 것도 같은 네 등급으로 매긴다.** "출근 성공률이 8% 떨어졌다"는 막힘이고,
"특정 기종에서만 실패한다"는 위험이다. **숫자가 붙은 항목은 같은 등급 안에서 먼저 고친다** —
몇 명이 겪는지 아는 항목이기 때문이다(§9). 반대로 **지켜보는 장치가 아예 없는 것**은 결함이
아니라 할 일이므로, 이 표로 등급을 매기지 말고 §8의 「없는 것」 칸에 적는다.

문구 전수 점검(15번)은 표 형식으로 바꾸고 기준 6개(어려운 말 / 막다른 안내 / 오류 문구 / 단정·광고 표현 /
현장 말과 다른 이름 / 부호·어투·오탈자)를 준다. 손님 화면이 있으면 **전역 §13**(손님에게 나가는 답은 확정하지 않는다)을 기준에 넣는다.

**영역 하나를 「지켜보는 장치·기록」으로 둔다.** 그 점검자가 §8의 있는 것·없는 것 표를 채워 온다.
관점은 여섯이면 된다. 타입·빌드 검사가 언제 도는가 / 핵심 경로 스모크가 있는가 / 권한 테스트가
있는가 / 실패가 조용히 넘어가는 곳이 있는가 / 무엇을 기록하고 있는가 / 되돌리기 절차가 적혀
있는가. **실데이터 접근은 여전히 금지**이니 기록은 정의(SQL·스키마)만 읽게 한다.

## 6. 하지 말 것

앞 절들의 규칙을 어기는 것들이다. **괄호 안 절 번호가 그 금지의 근거**이고,
찾기(§2) → 고치기(§3) → 지키기(§8·§9) 순서로 늘어놓았다.

- 1단계에서 고치기 시작하는 것. 사용자가 판단하기 전에는 보고만.
- 파일 이름·코드를 보고문에 넣는 것. 사장이 읽는 글이다.
- "~일 수 있다"로 근거 없이 늘리는 것. 항목 수보다 근거가 우선.
- 점검 에이전트에게 브라우저나 수정 권한을 주는 것.
- 점검 결과를 확인 없이 체크리스트에 옮기는 것. 틀린 주장이 섞여 온다.
- **화면을 한 번도 보지 않고 끝내는 것.** 코드만 읽으면 "안 되는 것"만 잡고
  "안 보이는 것"은 통째로 놓친다(2026-09-12 퇴사히어로에서 149건을 찾고도 그랬다).
- 시각 QA에 소스 코드를 같이 주는 것. 그림 대신 코드로 추측해 버린다.
- 시각 QA 결과를 코드 확인 없이 그대로 고치는 것. 렌더 차이일 수 있다.
- **한 번만 찍고 판정하는 것.** 짧게·길게 두 장을 견주지 않으면 로딩·애니메이션 중간을 결함으로 읽는다.
- **재지 않고 눈으로 본 것을 원인으로 단정하는 것.** 잴 수 있는 것은 재고 말한다(§2-5).
- **살아 있는 남의 화면에 시험 글자를 남기는 것**, 그리고 같은 조작을 세 번 넘게 다시 시도하는 것(§2-6).
- 결함 QA에 총점을 매기는 것. 점수 루프는 산출물 다듬기에만 쓴다(§0-1·§7).
- **캡차를 넣는 것**, 손님 화면에 외부 녹화 도구를 붙이는 것, 손님에게 설문으로 묻는 것(§9).
- 배포 전 점검만 하고 **지켜보는 장치 없이 끝내는 것.** 신고하지 못하는 손님은 조용히 떠난다(§8).

## 7. 점수로 루프를 돌릴 때 (산출물 다듬기만)

"95점 넘을 때까지 돌려라" 같은 지시는 **영상·디자인·문서처럼 내가 만든 산출물을 다듬을 때만** 받는다.
결함 QA에는 총점을 쓰지 않는다(§0-1). 2026-09-12 소개영상 42초를 이 방식으로 다듬었고 규칙은 셋이다.

- **항목을 먼저 적고 점수를 매긴다.** 훅·이해도·읽히는 속도·소리·화면 품질처럼 항목을 나누고,
  항목마다 **왜 그 점수인지 한 줄**을 쓴다. 근거 없는 총점은 스스로를 통과시키는 장치일 뿐이다.
- **내가 매긴 점수를 내가 못 믿을 때가 있다.** 화면을 다시 찍어 보거나(§2-4) 값을 재어(§2-5)
  확인되지 않으면 점수를 올리지 않는다. 「치치직」은 내가 92점을 주고 있던 구간에서 사용자가 듣고
  지적한 것이다. 귀로 들을 사람이 있으면 중간에 한 번 들려 준다.
- **한 번 통과한 항목도 뒤에 고친 것 때문에 깨진다.** 장면을 하나 넣으면 그 뒤 효과음의 위치가
  전부 밀린다. 순서·시간·색인에 의존하는 것은 고칠 때마다 다시 확인하고, 의존 관계를 파일 안에
  주석으로 남긴다.

## 8. 질을 유지하는 장치 — QA는 배포 전에 끝나지 않는다

앞의 절들(§1~§7)은 **한 번 훑어 찾고 고치는 일**이다. 서비스가 살아 움직이는 동안 질을 지키는
일은 성격이 다르다.
원칙 하나. **결함은 늦게 잡을수록 비싸다.** 그래서 막는 자리를 여섯 군데로 나누고, 프로젝트에
무엇이 있고 무엇이 없는지를 먼저 **조회해서 표로 적는다**(package.json 스크립트·CI 폴더·테스트
파일·에러 추적 유무). §2-5와 같은 규칙이다. **기억이나 앞 세션 요약으로 적지 않는다.**

| 자리 | 장치 | 무엇을 잡는가 |
|---|---|---|
| 쓰는 중 | 타입 검사 | 이름 틀린 필드, 없는 속성 |
| 커밋 전 | 훅으로 타입·빌드 한 번 | 안 되는 코드가 올라가는 것 |
| 배포 전 | **스모크 테스트 · 권한 테스트 · `site-qa`** | 핵심 경로가 죽은 것, 남의 데이터가 보이는 것 |
| 배포 중 | 한 곳에만 먼저 · 되돌리기 준비 | 전체가 한꺼번에 망가지는 것 |
| 배포 후 | **합성 감시 · 에러 추적** | 새벽에 죽은 것, 특정 기종에서만 실패하는 것 |
| 매일 | **건강 지표 한 개** · 사람 QA(§2) | 조용히 나빠지는 것 |

- **스모크 테스트 = 가장 짧은 진짜 사용 한 바퀴.** 화면 개수만큼 만들지 않는다. **돈이 오가는 길과
  매일 지나는 길만** 지킨다. 콕출근이면 셋이다. 출근 링크가 열리는가 · 사진을 올리면 기록되는가 ·
  서명하면 퇴근이 남는가. 이 셋이 초록이면 그날 서비스는 산 것이다.
- **권한 테스트를 테스트의 첫 자리에 둔다.** 저장 규칙(RLS·firestore.rules)은 자동 검증이 0인 채로
  남기 쉽고, 여기서 새면 되돌릴 수 없다. **A의 열쇠로 B의 명단을 읽어 0줄이 나와야 통과**하는
  짧은 스크립트 하나가 가장 값싼 보험이다(2026-09-12 콕출근 실측. SQL 파일 여럿, 자동 검증 0건).
- **합성 감시.** 몇 분마다 우리 대신 실제 링크를 눌러 보고 실패하면 대표에게 문자가 간다.
  **손님이 신고하지 못하는 서비스**에서는 이것이 테스트보다 먼저다(§9 첫 줄과 같은 이유).
- **에러 추적.** 개발 화면에서 재현되지 않는 고장(오래된 단말, 카카오톡 안에서 열린 브라우저,
  저장공간이 꽉 찬 폰)은 브라우저에서 터진 오류를 모아야 보인다.
- **되돌리기를 미리 한 번 해 본다.** 이전 배포로 돌리는 길을 급할 때 처음 해 보면 늦는다.
- **버그 하나에 검사 하나.** 고치기 전에 그 고장을 재현하는 검사를 먼저 만들고 그것을 초록으로
  만든다. 같은 고장이 두 번 오면 사고가 아니라 관리 실패다.
- **시각 회귀.** 주요 화면 여섯 장을 배포 전후로 찍어 견준다(§2-4의 촬영 명령 그대로). CSS 한 줄이
  다른 화면 다섯 곳을 망가뜨리는 일은 눈으로만 잡힌다.
- **건강 지표는 한 개면 된다.** 코드 지표(커버리지 같은 것)는 서비스의 질을 말해 주지 않는다.
  **업무가 성공한 비율**을 쓴다. 콕출근이면 「오늘 출근해야 할 인원 중 몇 %가 한 번에 성공했는가」.
  어제보다 떨어졌으면 무언가 고장 난 것이다.
- **하지 않는 것.** 커버리지 목표(전체 코드의 몇 %), 화면 조각 단위 테스트 대량 생산, 스냅샷 테스트
  남발. 백 개 남짓 파일 규모에서는 유지비만 늘고 잡는 것은 적다. **좁게, 대신 확실하게 지킨다.**

이 표에서 **없는 칸이 나오면 그것도 산출물이다.** 결함 목록에 섞지 않고(§4 마지막 줄) §2-7 보고
끝에 표로 붙이며, 2단계로 들어가면 체크리스트 「지킬 장치」 절(§3-1)이 그 자리를 받는다.

## 9. 실사용자가 어디서 막히는지 아는 법 (서비스가 돌기 시작한 뒤)

**신고할 수 없는 손님을 먼저 가정한다.** 어르신·환자·불안한 의뢰인은 화면이 안 열리면 신고하지 않고
그냥 포기하고 종이로 돌아간다. 그래서 "불만이 없다"를 잘 되고 있다는 뜻으로 읽으면 안 된다.

**쓰지 않을 두 가지를 먼저 정한다.**
- **캡차를 넣지 않는다.** 사람인지 가리는 그림 퍼즐은 불편을 찾는 장치가 아니라 만드는 장치다.
  글자를 읽고 옮겨 적는 일은 고령 사용자에게 사실상 통과 불가다. 본인 확인이 걱정이면 개인별
  문자 링크가 이미 그 역할을 한다.
- **외부 화면 녹화 도구(Clarity·Hotjar 류)를 손님 화면에 붙이지 않는다.** 이름·사진·위치가 그대로
  외부 서버로 나가고 처리위탁 업체가 하나 늘어 동의와 처리방침이 따라온다. 개인정보를 다루는
  화면에서는 얻는 것보다 잃는 것이 크다. 꼭 봐야 하면 **동의받은 직원·가족과 시험용 화면에서만** 쓴다.

**대신 그림 없이 숫자만 남긴다.** 「누가 무엇을 했나」가 아니라 「몇 번째 걸음에서 몇 초 걸렸나」다.
이름 대신 코드로 남기고, 내용(사진·글)은 저장하지 않고, 보관 기간을 정하고, 처리방침에 목적
한 줄을 넣는다. 이미 있는 기록 테이블을 먼저 찾아본다(콕출근은 `link_opens`가 도달 여부를,
`access_logs`가 취급자 열람을 법정 기준으로 남기고 있었다).

| 남기는 숫자 | 무엇을 가리키는가 |
|---|---|
| 권한 요청 거부·무응답 비율 | 묻는 창을 못 읽고 닫는다 |
| 화면 열고 일정 시간 안에 아무 것도 안 누르고 떠남 | 다음에 무엇을 눌러야 할지 모른다 |
| 실패 뒤 재시도 횟수 | 느린데 멈춘 것처럼 보인다 |
| 「지우고 다시」처럼 되돌리는 동작의 횟수 | 그 동작 자체가 어렵다 |
| 기종·브라우저별 실패율 | 특정 경로만 깨져 있다(앱 안에서 열린 브라우저가 흔한 범인) |
| 알림 받고 누르기까지 걸린 시간 | 알림을 못 찾거나 못 본다 |
| 시간대별 성공률 | 몰리는 시간에 느려진다 |

**손님이 남긴 산출물 자체가 증거다.** 콕출근은 사진과 시각을 이미 갖고 있다. 얼굴 사진이 올라왔으면
안내를 못 읽은 것이고, 한 아침에 같은 사람이 세 장이면 완료 화면이 약한 것이고, 캄캄한 사진이면
셔터 위치나 밝기 안내 문제다. **숫자보다 정직하니 표본으로 몇 장을 직접 본다.**

**숫자로 안 잡히는 것은 사람이 본다.**
- **설문은 하지 않는다.** "불편하셨어요"라고 물으면 거의 "괜찮아요"라고 답한다. 못 한 것을
  자기 탓으로 여기기 때문이다.
- **현장에서 다섯 명을 각 10분씩 말없이 본다.** 도와주지 않고 본다. 이것이 가장 많이 잡는다.
- **중간에서 대신 해 준 횟수를 센다.** "이번 주에 대신 찍어 드린 분이 몇 명입니까." **대리 처리
  건수가 곧 불편 지수**다. 그 숫자가 줄지 않으면 화면이 아직 어렵다.
- **걸려 온 전화와 물어본 내용이 그대로 개선 목록이다.**

**여기서 나온 숫자는 세 곳으로 돌아간다.** §2-7 보고의 근거가 되고, 반복되면 §4로 등급을 매겨
§3의 고치는 순서에 들어가고, **§1에서 그린 사람이 맞았는지 검산해 준다.** 기록이 예상과 다르면
고칠 것은 화면이 아니라 먼저 그 사람 묘사다.
