# 7대 페인포인트 기반 에이전트 역할 재설계 리서치

> 작성일: 2026-04-01
> 목적: 변호사 실무 페인포인트 7가지를 해결하기 위한 에이전트 역할 변경 방안

---

## 1. 페인포인트 vs 현재 커버리지

| # | 페인포인트 | 현재 담당 | 현재 커버리지 | 해결 방식 |
|---|-----------|----------|-------------|----------|
| PP1 | 의뢰인 정보 수집 구조화 실패 | 필묵 (docgen_questions) | **부분** — 문서 작성 전 확인용이지 인테이크가 아님 | 정적 체크리스트 (API 호출 0) |
| PP2 | AI 할루시네이션 (가짜 판례) | 판서 + ANTI_HALLUCINATION_RULES | **상당** — 법제처/RAG 기반 인용 규칙 있음 | 감수 프롬프트 확장 |
| PP3 | 서면 간 사실관계 불일치 | 없음 | **0%** | 혜안이 FactMaster JSON 생성 |
| PP4 | 서면 유형별 형식 표준 없음 | 필묵 (getDocTypeFormatTemplate) | **상당** — 14종 서식 템플릿 구현됨 | 변경 불필요 |
| PP5 | 증거-서면 연결 단절 | 혜안 (부분) | **20%** — 증거 구조도는 있으나 마스터 목록 없음 | EvidenceRegistry (시스템 기능) |
| PP6 | 반복 문서 비효율적 재생산 | 없음 | **0%** | 과거 유사문서 RAG 참조 |
| PP7 | 법령 개정 반영 지연 | 율무 (고지만 함) | **10%** | 법제처 법령 API 연동 |

### 핵심 발견

- **PP2, PP4는 이미 잘 커버됨** — 추가 에이전트 불필요
- **PP1은 정적 데이터** — Claude API 호출 없이 사건유형별 체크리스트만 추가
- **PP3, PP5, PP7은 시스템 인프라** — 에이전트가 아닌 DB/API 레이어
- **PP6은 RAG 확장** — 기존 Supabase 인프라 활용

## 2. 재설계 결론: 에이전트 6개 그대로 유지

**새 에이전트 0개, Claude API 추가 호출 0회.**

모든 개선이 **프롬프트 확장 + 시스템 인프라(Firestore + 법제처 API)**로 달성 가능.

| 에이전트 | 현재 역할 | 추가되는 역할 | 대응 PP |
|---------|----------|-------------|--------|
| **혜안** (analysis) | 쟁점 분석 + 논증 설계 | **+ FactMaster JSON 출력** (사실관계 구조화) | PP3 |
| **율무** (legal) | 관할/소송요건 | **+ 법령 현행 여부 경고** (StatuteChecker 결과 소비) | PP7 |
| **판서** (precedent) | 판례 검색 + ABC 분류 | 변경 없음 (이미 충분) | PP2 |
| **필묵** (docgen) | 체크포인트 + 문서 생성 | **+ 증거번호 마스터 연동 + 과거 유사문서 참조** | PP5, PP6 |
| **STT** | 음성 변환 | 변경 없음 | - |
| **감수** (review) | 품질 리뷰 | **+ 3중 검증** (사실관계 일관성 + 판례 실존 + 증거번호 정합성) | PP2, PP3, PP5 |

## 3. 시스템 기능 신규 3개 (에이전트가 아닌 인프라)

### 3-1. FactMaster — 사실관계 마스터 DB (PP3 해결)

사건 단위로 인물/날짜/금액/장소의 **단일 진실원본(Single Source of Truth)**.

**생성**: 혜안이 분석 시 아래 JSON을 함께 출력

```json
{
  "parties": [
    { "role": "원고", "name": "홍길동", "identifier": "800101-1******", "address": "서울시 강남구..." }
  ],
  "timeline": [
    { "date": "2024-03-15", "event": "금전소비대차계약 체결", "amount": 50000000, "evidence": "갑 제1호증" }
  ],
  "amounts": [
    { "label": "대여금 원금", "value": 50000000, "basis": "금전소비대차계약서" }
  ],
  "keyFacts": [
    { "fact": "변제기 2024.09.15 도과", "disputed": false, "evidence": "갑 제2호증" }
  ]
}
```

**소비**: 필묵이 서면 작성 시 이 데이터를 참조 → 날짜/금액/인물명 일관성 보장
**검증**: 감수가 서면 내 사실관계를 FactMaster와 교차검증
**저장**: Firestore `cases/{id}/factMaster`
**비용**: Claude API 추가 호출 0회 (혜안의 기존 호출에 출력 형식만 추가)

### 3-2. EvidenceRegistry — 증거 관리 레지스트리 (PP5 해결)

갑/을 제○호증 매핑 테이블. 증거 추가/삭제 시 전체 문서 자동 재넘버링.

```
갑 제1호증: 금전소비대차계약서 (2024.03.15)
갑 제2호증: 카카오톡 대화 캡처 (2024.06.20)
을 제1호증: 변제 영수증 (2024.09.01)
```

**필묵 연동**: 서면 작성 시 증거번호 마스터를 컨텍스트로 주입 → 정확한 증거번호 사용
**감수 검증**: 서면 내 증거번호가 마스터와 일치하는지, 누락/중복 없는지 확인
**저장**: Firestore `cases/{id}/evidences`
**비용**: Claude API 추가 호출 0회

### 3-3. StatuteVersionChecker — 법령 버전 검증기 (PP7 해결)

법제처 현행법령 API(`target=law`)로 인용 법조문의 현행 여부 확인.

```
✅ 민법 제750조 — 현행 (최종개정 2024.01.16)
⚠️ 공정거래법 제19조 — 2025.03.01 개정 시행
   개정이유: [법제처 제개정이유 필드]
   개정 전: [구 조문 내용]
   개정 후: [현행 조문 내용]
❌ 구 주택임대차보호법 제3조의2 — 2024.07.01 폐지
```

**율무 연동**: 소송요건 검증 시 법령 현행 여부 경고 포함
**판서 연동**: 판례의 참조조문이 개정된 경우 경고 첨부
**필묵 연동**: 개정된 조문 인용 시 "현행 [법령명 제○조] (YYYY.MM.DD 개정)" 형식
**저장**: `src/services/statute-api.ts` (신규)
**비용**: Claude API 추가 호출 0회, 법제처 API 호출 N회 (인용 조문 수, 무료)

## 4. 인테이크 체크리스트 (PP1 해결)

Claude API 호출 없이 **정적 데이터**로 구현:

```typescript
// src/config/intake-checklists.ts (신규 파일)
const INTAKE_CHECKLISTS: Record<CaseType, IntakeCategory[]> = {
  "민사": [
    { category: "당사자 정보", items: [
      "원고 성명/주민등록번호/주소",
      "피고 성명/주소 (송달 가능한 주소)",
      "대리인 위임장 징구 여부"
    ]},
    { category: "사실관계", items: [
      "분쟁 발생일 및 경위",
      "계약서/약정서 존재 여부",
      "금전 거래 내역 (이체 기록, 영수증)",
      "증인 존재 여부"
    ]},
    { category: "증거자료", items: [
      "계약서 원본/사본",
      "통장거래내역 (최근 1년)",
      "카카오톡/문자 대화 캡처",
      "내용증명 발송/수령 이력"
    ]},
    ...
  ],
  "형사": [...],
  "가사": [...],
  "행정": [...],
  ...
};
```

**사용 시점**: RecordPage에서 사건유형 선택 직후, 녹음/업로드 전에 체크리스트 UI 표시.
**비용**: 0원 (정적 데이터, API 호출 없음)

## 5. 감수 3중 검증 확장 (PP2+PP3+PP5 강화)

감수 프롬프트에 아래 검증 섹션 추가 (추가 API 호출 0회):

```
## 1. 사실관계 일관성 검증
[FactMaster]가 제공된 경우, 문서 내 모든 날짜/금액/인물명이 마스터와 일치하는지:
- 불일치: {위치} — 마스터: "{값}" / 문서: "{값}" → ⚠️ 수정 필요

## 2. 판례 실존 교차검증
인용된 모든 판례 사건번호가 [법제처 검색 결과] 또는 [RAG 검색 결과]에 존재하는지:
- 출처 미확인: {사건번호} → ⚠️ 삭제 또는 "판례상 확립된 법리에 의하면" 형태로 대체

## 3. 증거번호 정합성 검증
[EvidenceRegistry]가 제공된 경우:
- 문서의 증거번호가 마스터와 일치하는지
- 본문에서 인용했으나 입증방법에 누락된 증거는 없는지
- 입증방법에 있으나 본문에서 미인용된 증거는 없는지
```

## 6. 재설계 후 데이터 플로우

```
[상담 시작 전]
  IntakeChecklist (정적) ──→ 프론트엔드 UI (PP1)

[녹음/업로드 완료]
  STT ──→ transcript

[Stage 1] 5개 에이전트 병렬
  │
  ├─ 혜안: 쟁점 분석 + ★FactMaster JSON 생성 (PP3)
  │          → Firestore cases/{id}/factMaster 저장
  │
  ├─ 율무: 관할/소송요건 + ★법령 현행 여부 경고 (PP7)
  │          ← StatuteVersionChecker 결과 입력
  │
  ├─ 필묵: 체크포인트 질문 생성
  ├─ 감수: 예비 분석
  └─ STT: 음성 변환

[Stage 2] 판서 — 혜안의 쟁점을 받아 실행
  │
  ├─ 판례 서칭 (채널 A: RAG + 채널 B: 법제처)
  ├─ ABC 분류 + 인용/구별론 초안
  └─ ★참조조문 개정 여부 경고 (PP7)

[체크포인트 — 변호사 응답]

[Stage 3] 필묵 + 감수
  │
  ├─ 필묵 (최종 문서 생성)
  │    입력: 모든 에이전트 결과
  │         + ★FactMaster (PP3 — 날짜/금액/인물 일관성)
  │         + ★EvidenceRegistry (PP5 — 정확한 증거번호)
  │         + ★과거 유사문서 (PP6 — 참조)
  │         + ★법령 검증 결과 (PP7)
  │         + 체크포인트 응답
  │
  └─ 감수 (3중 검증)
       ① 사실관계 일관성 (FactMaster 대조) — PP3
       ② 판례 실존 교차검증 — PP2
       ③ 증거번호 정합성 — PP5
```
