## 2. 슈퍼로이어의 인용 시스템 분석 (실제 동작 방식)

슈퍼로이어의 인용 시스템은 4가지 참조 체계로 구성:

### 판례 인용
- 형식: `(법원명 선고일자 선고 사건번호 판결)`
- 예: `(대법원 2000. 12. 8. 선고 99도214 판결)`
- 우선순위: **상급심 > 최신 판례 > 판례요지 우선**
- 데이터: **빅케이스(BigCase) DB 기반**, 매일 업데이트
- 원칙: **"참조 자료(references) 내에 실제로 존재하는 판례만 인용, 존재하지 않는 자료를 임의로 만들지 않음"**

### 교과서 인용 — BookPageID 시스템
- 형식: `(BookPageID: N)` — 내부 고유 식별자로 관리
- 표시: `(권순현 외 2인, 『공직법입문』, 박영사(2018년), 172-173면)`
- 데이터: **박영사 1,350종/100만 페이지 독점 라이선스**
- 각 페이지에 고유 ID가 부여되어 정확한 출처 추적 가능

### 사용자 문서 인용 — DocPageID 시스템
- 형식: `(DocPageID: N-P-I)` 또는 `(DocPageID: N-P)`
- 업로드된 PDF/문서의 페이지 단위로 ID 부여
- 본문에서 "계약서 제3조에 따르면..." 등으로 정확한 페이지 참조

### 법령 인용
- 형식: `(법령명 제○조 제○항)`
- 예: `(저작권법 제28조)`

## 3. 치명적 격차 6가지

### 격차 1: 판례 인용 전무 (가장 심각)

슈퍼로이어: `(대법원 2000. 12. 8. 선고 99도214 판결)` — 빅케이스 DB에서 실존 확인 후 인용
로캐디: 없음

- 한국 소송에서 판례 없는 소장 = "법리 검토 없이 사실만 나열"이라는 신호
- 2026년 법원: AI 허위 판례 인용 시 과태료 추진 중 — 하지만 **인용이 전혀 없는 것**도 문제
- 슈퍼로이어의 핵심: **"references 내 실존하는 것만 인용"** 원칙 + 빅케이스 매일 업데이트 DB

### 격차 2: 교과서/학술 인용 없음

슈퍼로이어: BookPageID로 관리 → `(송덕수, 『채권법총론[제7판]』, 박영사(2024년), 264면)`
로캐디: 없음

- 슈퍼로이어는 **페이지 단위 ID 시스템**으로 정확한 출처 추적
- 박영사 독점 라이선스로 교과서 본문까지 RAG에 투입

### 격차 3: 증거-파일 매핑 부정확

슈퍼로이어: **DocPageID 시스템** — 업로드 문서의 페이지별 고유 ID로 정확한 참조
로캐디: 파일 참조는 있으나 `갑 제N호증` 체계와 연결 안 됨, 페이지 단위 추적 없음

### 격차 4: 청구취지 불명확

슈퍼로이어:
```
1. 채권양도계약을 취소한다.
2. 금 230,916,900원 및 이에 대하여... 연 5%...
3. 소송비용은 피고 부담
4. 제2항은 가집행할 수 있다.
```

로캐디: "원상회복하라" (무엇을 어떻게? → 집행 불가)

### 격차 5: 별지(別紙) 없음

슈퍼로이어: 구체적 학교명/채무자 정보가 담긴 별지
로캐디: 본문에 모두 기재 → 가독성 저하

### 격차 6: 플레이스홀더 잔존

로캐디: `【여기에 피고의 정확한 주소를 기재하세요】` — 그대로 제출 시 즉시 보정명령

## 4. 격차 해소를 위한 기술 구현 방안

### 4-1. 판례 인용 시스템 (C 영역 0→20점)

**MVP (프롬프트만, 즉시 가능):**
- 필묵 프롬프트에 인용 형식 강제: `대법원 YYYY. M. D. 선고 사건번호 판결`
- 판서가 검색한 실존 판례의 사건번호를 필묵이 그대로 인용하도록 지시
- 현재 `formatPrecedentsForPrompt()`가 이미 사건번호/선고일을 넘기고 있음

**Phase 2 (인용 검증 파이프라인):**
```typescript
// 문서 생성 후 정규식으로 사건번호 추출 → 법제처 API로 실존 확인
const CASE_NUMBER_REGEX = /\d{4}[가-힣]{1,4}\d{3,7}/g;
// 존재하지 않는 사건번호 발견 시 경고 또는 자동 제거
```

**Phase 3 (판례 DB 확충):**
- Supabase RAG에 판례 5,000→50,000건 단계적 확대
- 사건 유형별 리딩케이스 사전 매핑

### 4-2. 조문 전문 인용 (B 영역 +5점)

법제처 법령 API(`target=law`)로 조문 전문 조회:
```
혜안이 식별한 법조문 → 법제처 API로 조문 텍스트 조회 → 필묵에게 전달

결과:
"민법 제406조 제1항: 채무자가 채권자를 해함을 알면서 재산권을 목적으로 한 
법률행위를 한 때에는 채권자는 그 취소 및 원상회복을 법원에 청구할 수 있다."
```

비용: 법제처 API 무료, Claude API 추가 호출 0회

### 4-3. 증거번호-파일 매핑 (E 영역 4→9점)

```
업로드 파일 → 자동 "갑 제N호증" 부여 → OCR/텍스트 추출 → 증거 설명 생성
→ 필묵이 본문에서 "(갑 제1호증 3쪽)" 형태로 정확히 인용
```

EvidenceRegistry (Phase 2 플랜에 이미 포함)

### 4-4. 청구취지 정밀화 (A+B 영역 +8점)

```typescript
// 사건유형별 청구취지 계산기
```


## 6. 슈퍼로이어 인용 시스템을 참고한 로캐디 구현 방안

### 로캐디 버전 인용 ID 시스템

슈퍼로이어의 BookPageID/DocPageID를 참고하되, 로캐디의 기술 스택에 맞게 설계:

**CaseRefID — 판례 참조 ID**
```
판서가 검색한 판례에 고유 ID 부여:
  CaseRef-1: 대법원 2017. 11. 29. 선고 2017다241819 판결 (법제처 판례일련번호 기반)
  CaseRef-2: 대법원 2013. 4. 11. 선고 2012다107198 판결

필묵이 인용 시:
  "사해의사는 추정된다(CaseRef-1)."
  → 최종 출력: "사해의사는 추정된다(대법원 2017. 11. 29. 선고 2017다241819 판결)."
```
구현: 판서 산출물에 판례 목록을 JSON으로 포함, 필묵이 ID로 참조 후 최종 치환

**DocRefID — 업로드 문서 참조 ID**
```
업로드 파일에 자동 ID 부여:
  DocRef-1: 사행행위 공문.pdf (갑 제1호증)
  DocRef-2: 채권가압류 결정서.pdf (갑 제2호증)
  DocRef-1-P3: 사행행위 공문.pdf 3쪽

필묵이 인용 시:
  "원고는 피고에게 내용증명을 발송하였다(DocRef-1-P1)."
  → 최종 출력: "원고는 피고에게 내용증명을 발송하였다(갑 제1호증)."
```
구현: EvidenceRegistry와 연동, OCR 추출 시 페이지 번호 추적

**StatuteRefID — 법령 참조 ID**
```
혜안이 식별한 법조문에 ID 부여:
  StatRef-1: 민법 제406조 제1항
  StatRef-2: 민사소송법 제213조

법제처 API로 조문 전문 조회 후 캐싱
필묵이 인용 시 조문 전문과 함께 정확하게 인용
```

### 인용 우선순위 규칙 (슈퍼로이어 방식 준용)

필묵 프롬프트에 추가:
```
[인용 우선순위 — 반드시 준수]
1. 대법원 판례 > 고등법원 판례 > 지방법원 판례
2. 최신 판례 우선 (동일 법리 다수 판례 시)
3. 판례요지(판시사항/판결요지)를 인용 근거로 우선 사용
4. 참조 자료에 실제로 존재하는 판례·법령·증거만 인용
5. 존재하지 않는 자료를 임의로 만들어 인용하지 않음
```

### 인용 검증 파이프라인 (감수 에이전트 연동)

```
필묵 문서 생성 완료
  ↓
감수 3중 검증 중 "판례 실존 교차검증":
  1. 문서에서 사건번호 정규식 추출
  2. 각 사건번호를 판서의 검색 결과(CaseRef 목록)와 대조
  3. 판서 목록에 없는 사건번호 발견 시:
     ⚠️ "이 사건번호는 판서의 검색 결과에 없습니다. 환각(hallucination) 가능성."
  4. 추가로 법제처 API로 실존 확인 (선택적)
```

| 기능 | 사건번호 입력 → 실존 여부 확인 + 존재 시 판결 내용 안내 |

### API 가용 여부

| 소스 | API | 사건번호 검증 |
|------|-----|-------------|
| **사법정보공개포털** (portal.scourt.go.kr) | **공개 API 없음** (웹 전용) | 직접 호출 불가 |
| **사법정보공유포털** (openapi.scourt.go.kr) | 제한적 (기관 간 연계) | 별도 문의 필요 |
| **법제처 API** (law.go.kr) | **이미 통합됨** | query에 사건번호 입력으로 검증 가능 |

### 권장: 법제처 API 기반 검증 (즉시 가능)

law-caddy의 `precedent-search.ts`에서 이미 법제처 API를 호출하고 있으므로, **사건번호를 query에 넣어 검색하면 실존 여부를 검증**할 수 있다.

```
검증 흐름:
1. 필묵이 생성한 문서에서 사건번호 정규식 추출: /\d{4}[가-힣]{1,4}\d+/g
2. 각 사건번호를 법제처 API로 검색 (query=사건번호, display=1)
3. 검색 결과에서 정확히 일치하는 사건번호가 있으면 → ✅ 실존
4. 없으면 → ⚠️ 미확인 (허위 가능성)
```

### 구현 계획

**Phase 1 (즉시):**
- `/api/case-verify` 엔드포인트 신설 — 배치 검증 지원
- 감수 에이전트 후처리로 자동 검증 — Stage 4 추가
- UI에 검증 배지: `[✅ 실존]` / `[⚠️ 미확인]`

**Phase 2 (중기):**
- 대법원에 API 접근 문의 (`publicapi@scourt.go.kr`)
- 헌재 결정례(detc) + 법령해석례(expc) 교차검증 추가

**Phase 3 (장기):**
- 대법원 공식 API 출시 시 전환
- 자체 판례 DB(Supabase)와 이중 검증

### 한계점

- 법제처 DB에 등록된 공개 판례만 검증 가능 (비공개/하급심 일부 누락)
- 최신 판결은 DB 등재까지 시간 소요
- 헌재 결정례는 `target=detc`로 별도 검색 필요

### 차별화 기회

현재까지 **대법원 허위 사건번호 확인 서비스를 API로 자동 통합한 리걸테크 제품은 확인되지 않음**. law-caddy가 이를 최초로 구현하면 다음 차별점을 가짐:

- 문서 생성 시 자동으로 모든 인용 판례 실존 확인
- 허위 판례 인용 즉시 경고 → 변호사 징계 사전 방지
- "AI 생성 문서이지만 모든 판례가 검증됨" — 법원 신뢰도 확보
