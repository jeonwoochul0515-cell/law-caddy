# 판례 검색 품질 개선 리서치

> 현재 시스템의 판례 검색 파이프라인을 분석하고, 양질의 판례를 검색하기 위한 개선 방안을 도출한다.

---

## 1. 현재 시스템 분석

### 1.1 현재 3-Stage 파이프라인

```
[Stage 1] 서혜안(쟁점 분석) + 윤율무 + 정소리 + 조필묵 질문 — 병렬 실행
    ↓
    서혜안 결과에서 IssueWithKeywords[] JSON 파싱
    ↓
[Stage 2] 한판서(판례 검색) — 서혜안의 쟁점 + 키워드로 검색
    ↓
    한판서 결과에서 CaseRef[] JSON 파싱
    ↓
[Stage 3] 최감수(검토) — 모든 에이전트 결과 + CaseRef로 3중 교차검증
```

### 1.2 현재 한판서의 검색 알고리즘

```
각 쟁점(issue)에 대해:
  각 키워드(keyword)에 대해:
    1. 법제처 API로 판례 검색 (keyword, limit=15)
    2. 헌재결정례 검색 (keyword, limit=2)
    3. 300ms 딜레이 (rate limit 방지)

  상위 3건에 대해:
    4. 판례 본문 상세 조회

  5. 프롬프트용 마크다운 포맷팅
```

### 1.3 RAG 인프라 (현재 존재하지만 활용 부족)

| 테이블 | 내용 | 건수 |
|--------|------|------|
| cases | 실제 판례 전문 | 41만건 |
| legal_judgments | 분석된 판결 | - |
| statutes | 법조문 | - |
| legal_commentary | 법학 해설 | - |
| aihub_legal_qa | 법률 Q&A | - |

- **Voyage AI** (voyage-3) 임베딩 + Supabase 벡터 검색 인프라 존재
- **Voyage Rerank** (rerank-2.5) 재순위화 인프라 존재
- **한국어 전처리** (korean-preprocessor.ts) — 조사 제거, 복합명사 분해, 동의어 확장

## 2. 현재 시스템의 핵심 약점

### 2.1 법조문 기반 검색 미사용 (가장 치명적)

현재 한판서는 **키워드만으로 검색**한다. 법제처 API에는 `JO` 파라미터(참조조문 검색)가 있지만 **전혀 사용하지 않고 있다**.

```
현재: query="손해배상" → 키워드 매칭으로 판례 검색
개선: JO="민법" + query="제750조 손해배상" → 해당 조문을 해석한 판례 검색
```

**왜 중요한가**: 실무에서 변호사가 판례를 찾을 때 가장 먼저 하는 것은 **관련 조문을 특정한 뒤, 그 조문을 해석한 판례를 찾는 것**이다. 키워드만으로는 노이즈가 많고 핵심 리딩케이스를 놓친다.

### 2.2 서혜안 → 한판서 핸드오프 구조의 한계

서혜안이 출력하는 JSON 구조:
```json
[{
  "id": 1,
  "issue": "불법행위 성립 여부",
  "keywords": ["불법행위", "손해배상"],
  "priority": "high"
}]
```

**문제점**:
- `keywords`에 **법조문 정보가 없다** (예: "민법 제750조")
- 키워드가 너무 범용적이다 ("손해배상"으로는 10만건이 나온다)
- JSON 파싱 실패 시 폴백이 14개 하드코딩 패턴뿐이다

### 2.3 RAG 벡터 검색이 판례 에이전트에 미사용

41만건 판례 DB가 Supabase에 있고, Voyage 임베딩/리랭킹 인프라도 있지만 **Stage 2 한판서는 RAG를 사용하지 않고 법제처 API만 호출한다**.

- Stage 1에서 RAG 검색은 실행되지만, 그 결과가 한판서에 충분히 전달되지 않음
- 시맨틱 유사도 기반 판례 검색의 이점을 전혀 활용하지 못함

### 2.4 판례 환각(Hallucination) 방어가 프롬프트 의존적

현재 방어:
- 프롬프트에 "검색 결과에 없는 사건번호를 만들지 마세요" 지시
- 최감수가 CaseRef와 대조 검증

**한계**: Claude가 프롬프트 지시를 무시하고 존재하지 않는 판례를 생성할 수 있다. 기술적 검증(법제처 API로 사건번호 실존 확인)이 없다.

### 2.5 리딩케이스 vs 보강 판례 구분 없음

현재 한판서는 검색 결과를 "유리/불리"로만 분류한다. **대법원 전원합의체 판결(리딩케이스)과 하급심 적용 판례를 구별하지 않아**, 중요도 없이 나열되는 문제가 있다.

### 2.6 판례 유효성(폐기 여부) 미검증

대법원 전원합의체가 기존 판례를 변경(폐기)한 경우, 폐기된 판례를 인용하면 치명적이다. 현재 **판례 폐기 여부를 확인하는 로직이 없다**.

## 3. 개선 방안: 4단계 파이프라인

### 3.1 권장 파이프라인 (현재 3단계 → 4단계)

```
[Stage 1] 서혜안: 쟁점 분석 + 법조문 매핑 (기존 + 강화)
    ↓
    출력: IssueWithStatutes[] — 쟁점 + 관련 법조문 + 검색 키워드
    ↓
[Stage 2-A] 한판서: 법조문 기반 판례 검색 (법제처 JO 파라미터)
[Stage 2-B] 한판서: RAG 시맨틱 검색 (Supabase 벡터 DB)
[Stage 2-C] 한판서: 키워드 검색 (현재 방식, 보조)
    ↓
    3개 소스 결과 병합 + Voyage Rerank로 재순위화
    ↓
[Stage 3] 한판서: 판례 분석 & CaseRef 생성
    ↓
[Stage 4] 최감수: 3중 교차검증 + 사건번호 실존 확인
```

### 3.2 서혜안 출력 구조 강화

**현재**:
```json
[{"id":1, "issue":"...", "keywords":["손해배상","불법행위"], "priority":"high"}]
```

**개선**:
```json
[{
  "id": 1,
  "issue": "불법행위에 기한 손해배상청구권 성립 여부",
  "statutes": [
    {"law": "민법", "article": "제750조", "content": "불법행위의 성립요건"},
    {"law": "민법", "article": "제751조", "content": "재산 이외의 손해배상"},
    {"law": "민법", "article": "제763조", "content": "준용규정"}
  ],
  "searchQueries": {
    "statute": ["민법 제750조", "민법 제751조"],
    "keyword": ["불법행위 손해배상 과실", "위법성 상당인과관계"],
    "semantic": "피고의 과실로 인한 불법행위가 성립하는지, 손해와의 인과관계가 인정되는지"
  },
  "caseType": "leading",
  "priority": "high"
}]
```

**핵심 변경점**:
- `statutes[]` 추가 — 관련 법조문을 명시적으로 매핑
- `searchQueries` 3종 분리 — 법조문 검색용, 키워드 검색용, 시맨틱 검색용
- `caseType` — "leading"(리딩케이스 필요) vs "supporting"(보강 판례)

### 3.3 한판서 검색 전략: 3-Source 병합

#### Source A: 법조문 기반 검색 (신규, 최우선)

```
법제처 API:
  JO="민법" + query="제750조" → 민법 제750조를 해석한 판례
  org=400201 (대법원) 우선 → 리딩케이스 확보
  org=400202 (하급심) 보조 → 구체적 사실관계 참고
```

**왜 이것이 가장 효과적인가**:
- 법조문은 법률 체계의 **좌표**다. 좌표로 검색하면 정확한 판례가 나온다
- "손해배상"이라는 키워드는 10만건이지만, "민법 제750조"로 좁히면 핵심 판례만 남는다
- 대법원 판례 중 **해당 조문의 해석 기준을 세운 판례**(리딩케이스)를 자연스럽게 찾게 된다

#### Source B: RAG 시맨틱 검색 (기존 인프라 활용)

```
Supabase 벡터 검색:
  쿼리: 서혜안의 semantic 검색어
  테이블: cases + legal_judgments
  임베딩: Voyage-3
  리랭킹: Voyage Rerank 2.5
```

**장점**: 키워드에 포함되지 않는 유사 법리의 판례를 발견할 수 있다
- "계약 위반" → "채무불이행" 판례도 시맨틱으로 매칭
- 사실관계가 유사한 판례 발견 (키워드만으로는 불가)

#### Source C: 키워드 검색 (현재 방식, 보조)

```
법제처 API:
  query="손해배상 과실 상당인과관계" (복합 키워드)
  최근 5년 우선 필터링
```

### 3.4 검색 결과 병합 & 재순위화

```
3개 소스 결과 수집 (각 10~15건)
    ↓
중복 제거 (사건번호 기준)
    ↓
Voyage Rerank 2.5로 통합 재순위화
    ↓
법원 계층 가중치 적용:
  - 대법원 전원합의체: x1.5
  - 대법원: x1.0
  - 고등법원: x0.7
  - 지방법원: x0.5
    ↓
최종 상위 5~8건 선택
```

### 3.5 판례 분석 출력 구조 개선

**현재 CaseRef**:
```json
{"id":"CaseRef-1", "court":"대법원", "caseNumber":"2017다241819", "group":"A", "keyHolding":"..."}
```

**개선 CaseRef**:
```json
{
  "id": "CaseRef-1",
  "court": "대법원",
  "division": "전원합의체",
  "caseNumber": "2017다241819",
  "date": "2017. 11. 29.",
  "caseType": "leading",
  "group": "A",
  "relatedStatutes": ["민법 제750조", "민법 제751조"],
  "keyHolding": "핵심 판시사항",
  "factSimilarity": "high",
  "distinguishStrategy": null,
  "overruled": false,
  "source": "law.go.kr"
}
```

**추가 필드**:
- `division` — "전원합의체" 여부 (리딩케이스 판별)
- `caseType` — "leading" / "supporting" / "adverse" (리딩케이스/보강/불리)
- `relatedStatutes` — 이 판례가 해석한 법조문
- `factSimilarity` — 본 사건과의 사실관계 유사도 (high/medium/low)
- `overruled` — 폐기 여부
- `source` — 출처 (law.go.kr / rag-db / constitutional)

## 4. 서혜안 프롬프트 개선안

### 4.1 법조문 매핑 지시 추가

현재 서혜안 프롬프트의 "검색 키워드 JSON" 부분을 다음으로 교체:

```
## 한판서 연동용 — 쟁점별 검색 설계 (JSON)

각 쟁점에 대해 다음 3가지 검색 전략을 설계하세요:

[{
  "id": 1,
  "issue": "쟁점명",
  "statutes": [
    {"law": "법률명", "article": "조항", "content": "해당 조문의 핵심 내용"}
  ],
  "searchQueries": {
    "statute": ["법률명 조항"],
    "keyword": ["법률 전문용어 조합 (2~4개 단어)"],
    "semantic": "이 쟁점의 법리를 자연어로 서술한 문장"
  },
  "priority": "high|medium|low"
}]

### 법조문 매핑 규칙
- 각 쟁점에 대해 **근거 법조문을 반드시 1개 이상** 매핑
- 법률명은 약칭 불가 (민법, 형법, 상법, 근로기준법 등 정식 명칭)
- 조문 번호를 확신할 수 없으면 "법률명 [조문 확인 필요]"로 표시
- 특별법 우선: 일반법(민법)보다 특별법(주택임대차보호법 등)을 우선 매핑

### 검색 키워드 설계 규칙
- keyword: 법률 전문용어 위주, 2~4개 단어 조합 (예: "채무불이행 손해배상 상당인과관계")
- semantic: 판사가 판결문에 쓸 법한 자연어 문장 (예: "원고의 계약 해제가 적법한지 여부")
- statute: "법률명 제N조" 형태 (법제처 API JO 파라미터용)
```

## 5. 한판서 프롬프트 개선안

### 5.1 검색 전략 지시 추가

```
## 검색 전략

서혜안이 설계한 searchQueries를 활용하여 다음 순서로 판례를 분석하세요:

### 1순위: 법조문 해석 판례 (리딩케이스)
- 각 쟁점의 statutes에 명시된 법조문을 해석한 대법원 판례를 우선 분석
- 대법원 전원합의체 판결 → 대법원 판결 → 고등법원 판결 순서
- "최초로 이 법리를 선언한 판결"을 리딩케이스로 표시

### 2순위: 사실관계 유사 판례 (보강)
- 본 사건과 사실관계가 유사한 하급심 판례
- 리딩케이스의 법리를 구체적 사안에 적용한 사례

### 3순위: 불리한 판례 & Distinguish 전략
- 상대방이 인용할 가능성이 높은 판례
- 왜 본 사건에 직접 적용되지 않는지 구별(Distinguish) 논거 제시

### 판례 유효성 확인
- 전원합의체 판결로 폐기·변경된 판례가 아닌지 확인
- 폐기된 판례를 발견하면 "[폐기됨]" 표시 + 변경 판례 함께 제시
```

### 5.2 판례 분석 깊이 강화

```
## 각 판례 분석 형식

### [CaseRef-N] 사건번호 (법원, 선고일) 🟢
- **판례 유형**: 리딩케이스 / 보강 판례 / 불리 판례
- **해석 법조문**: {이 판례가 해석한 법조문}
- **사안 요약**: {사실관계 3~4문장}
- **핵심 법리**: {판시사항 핵심 — 판결문 원문 인용}
- **요건사실 분석**:
  ① {요건 1}: 충족 여부 + 근거
  ② {요건 2}: 충족 여부 + 근거
- **본 사건 적용**:
  - 유사점: {사실관계·법률관계의 유사성}
  - 차이점: {구별되는 부분과 결론에 미치는 영향}
- **활용 전략**: {이 판례를 서면에서 어떻게 인용할지}
```

## 6. 최감수 검증 강화안

### 6.1 판례 실존 교차검증 (기술적 검증 추가)

현재는 프롬프트 기반 검증만 수행. 다음을 추가:

```
검증 파이프라인:
  1. CaseRef의 사건번호로 법제처 API 재조회
  2. 조회 실패 → "[미확인]" 마킹 + 경고
  3. 조회 성공 → 법원명·선고일 교차 대조
  4. 불일치 → "[정보 불일치]" 마킹 + 실제 정보로 교정
```

### 6.2 판례-조문 정합성 검증

```
최감수 추가 검증 항목:
  - 본문에서 인용한 법조문이 실제 존재하는지
  - 인용한 판례가 해당 법조문을 실제로 해석한 것인지
  - 판례의 판시사항과 본문 인용 내용이 일치하는지
```

## 8. 핵심 결론

### 현재 가장 큰 문제

> **한판서가 "법조문 → 판례" 경로를 사용하지 않고 키워드만으로 검색하고 있다.**
> 이것은 변호사가 판례를 찾을 때 "관련 조문을 먼저 특정하고, 그 조문을 해석한 판례를 찾는" 실무 워크플로우와 완전히 다르다.

### 가장 효과적인 개선

1. **서혜안이 법조문을 매핑**하도록 프롬프트 강화 → 코드 변경 없이 즉시 가능
2. **법제처 API JO 파라미터**로 법조문 기반 판례 검색 추가 → 검색 정확도 극적 향상
3. **RAG 41만건 판례 DB**를 한판서에 직접 활용 → 이미 인프라가 있으므로 연결만 하면 됨
4. **리딩케이스 식별** (전원합의체, 최초 법리 선언) → 중요도 순서 제공

### 변호사처럼 판례를 찾는 방법

```
1. 사건 → 쟁점 도출 (서혜안)
2. 쟁점 → 관련 법조문 특정 (서혜안 강화)
3. 법조문 → 리딩케이스 검색 (한판서 Phase 2)
4. 리딩케이스 → 사실관계 유사 판례 확장 (RAG Phase 3)
5. 불리한 판례 → Distinguish 전략 수립 (한판서 기존)
6. 판례 실존·유효성 검증 (최감수 Phase 4)
```

이것이 **최고의 법률 전문가가 판례를 찾는 방식**이며, 현재 시스템은 3단계만 부분적으로 수행하고 있다.
