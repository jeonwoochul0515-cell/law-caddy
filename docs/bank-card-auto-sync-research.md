# 카드/계좌 거래내역 자동 가져오기 — 심층 고찰

> 작성일: 2026-04-11
> 대상: LAW-CADDY (한국 1인 변호사 B2B SaaS, React + Firebase + Claude)
> 범위: 기존 CODEF 기반 구현 진단 + 대안 검토 + MVP 권장안

---

## TL;DR (5줄)

1. **현재 CODEF 연동은 "껍데기 80% + 알맹이 30%" 상태다.** 프론트 UI·Firestore 스키마·AI 매칭 오케스트레이터는 전부 구현돼 있지만, `/api/codef/*` 백엔드 프록시가 실제로 존재·배포·동작하는지 코드베이스로는 확인되지 않으며, 인증 시크릿·암호화 저장·재시도·페이지네이션 등 프로덕션 필수 요소가 비어 있다.
2. **법적 리스크가 가장 큰 숨은 지뢰다.** CODEF는 합법적으로 운영되지만, SaaS가 변호사의 인터넷뱅킹 ID/PW 또는 공동인증서를 "위탁 처리"하는 것은 전자금융거래법·개인정보보호법 관점에서 해석 논쟁이 있는 회색지대이며, 변호사 직역 특성상 한 건이라도 사고 나면 서비스 평판이 직격탄이다.
3. **4~6주 MVP 기준 최선은 Option B = "수기 CSV 업로드 + AI 분류" 우선, CODEF는 Phase 2.** 기존 `bankMatcher.ts`/`cardClassifier.ts`의 80%는 그대로 재사용 가능하다 (업로드 파서만 갈아끼우면 됨).
4. **장기적으로는 Option C (오픈뱅킹 + 본인 확인 기반 마이데이터 파트너)로 이전하는 게 안전하다.** CODEF는 "빠른 프로토타입 → 검증 → 정식 채널" 루트의 첫 단계로만 쓰는 게 이상적이다.
5. **지금 당장 할 일: ① codefApi.ts 프록시 상태 검증, ② CSV 업로드 파서 1주 스프린트로 붙이기, ③ CODEF는 내부 플래그로 비활성화해 베타에서 숨기기.**

### 1.2 "진짜 작동하는 상태인가?" 체크리스트

| 항목 | 상태 | 근거 |
|---|---|---|
| 사용자가 은행 선택 → 인증 → 거래내역 수신 E2E | ❌ 추정 미작동 | 백엔드 프록시 부재 또는 미검증 |
| CODEF `connectedId` Firestore 저장 | 🟢 구현됨 | `createCodefAccount` 호출 확인 |
| **비밀번호/공동인증서 암호화 저장** | ❌ **없음** | 코드상 Firestore에는 `connectedId`만 저장. 그러나 CODEF 측이 해당 자격증명을 평문 보관한다면 여전히 리스크는 존재 (CODEF 책임이지만 계약상 위탁자 공동책임 가능). |
| 거래 중복 방지 | 🟢 구현됨 | 은행은 `transactionHash = 날짜_시간_금액_상대방`, 카드는 `approvalNumber` |
| **재시도 로직 / 백오프** | ❌ 없음 | 단일 fetch. CODEF 500/타임아웃 시 그대로 실패. |
| **페이지네이션 / 대용량 처리** | ❌ 없음 | 30일치를 한 번에 받는다고 가정. 활발한 카드는 월 수백 건 가능. |
| **스케줄 자동 동기화** | ❌ 없음 | 오직 수동 "동기화" 버튼. Firebase Functions 크론 없음. |
| `bankMatcher.ts` vs `CodefSyncTab.tsx` 로직 분기 | ⚠️ 중복 | 오케스트레이터는 있는데 UI가 안 쓰고 날것 API를 직접 호출 → **AI 매칭이 실제 사용자 플로우에서 돌지 않을 가능성** |
| 민감정보 로깅 방지 | ⚠️ 검증 필요 | `console.error(err)`가 비밀번호 포함 요청 본문을 찍을 여지 |
| Firestore 보안 규칙에서 `bank_transactions`/`card_transactions`/`codef_accounts` 컬렉션 보호 | ❓ 미확인 | 이 저장소 룰 파일 별도 검토 필요 |

**결론:** "시연 데모는 되지만 프로덕션에는 절대 못 올리는 상태." 가장 위험한 건 UI가 오케스트레이터를 우회해서 AI 매칭 자동화가 실제로 베타 사용자에게 제공되지 않는 점, 그리고 백엔드 프록시 존재 여부가 불명확한 점.

## 2. CODEF 서비스 심층 분석

### 2.1 기본 정보 (2026-04 기준)

- **운영사:** 쿠콘(주) (Coocon). 코스닥 상장(294570). EDI·스크래핑·오픈뱅킹 20년차 인프라 사업자.
- **CODEF = 쿠콘이 외부 개발자/핀테크에 제공하는 구독형 API 게이트웨이** (bank/card/tax/public 전 분야 커버).
- **스크래핑 합법성 변화:** 2022-01 이후 **마이데이터 사업자는** 스크래핑 금지, API 의무 사용 (전자금융거래법·신용정보법 개정). 그러나 **"마이데이터 사업자가 아닌 일반 기업"이 이용자 본인 위임으로 스크래핑 하는 것 자체는 여전히 합법 회색지대**로 운영된다. CODEF는 이 틈에서 "비(非)마이데이터 라이선스 기업도 금융데이터에 접근할 수 있는 우회로"로 자리매김했다.
- **인증 방식:** 공동인증서, ID/PW, 카카오·PASS·네이버 간편인증, 일부는 오픈뱅킹 정식 API 재포장.
- **지원 기관:** 1군 은행 전부(신한/국민/하나/우리/기업/농협/SC/인뱅3사) + 주요 카드사(삼성/신한/KB/현대/롯데/BC/NH) + 홈택스·위택스·건보·국민연금 등.

**변호사 1명 기준 월 예상 CODEF 비용 (추정):**
- 사업용 은행 1개 × 월 1회 동기화 × 평균 80건 = 80콜
- 사업용 카드 1장 × 월 1회 동기화 × 평균 60건 = 60콜
- 인증 재발급 월 0~2회

**LAW-CADDY 요금제와의 충돌점:** Pro 89,000원 플랜 내에서 Claude API 원가(건당 상당)와 CODEF 원가가 동시에 나가면 마진 압박. **사용자 100명 기준 월 CODEF 비용 50만~150만 원**은 부담 가능하지만, 기본료 구조에 따라 초기 10~30명 단계에선 단가가 비싼 편.

### 2.3 CODEF의 실제 장단점

**장점**
- 빠른 개발: ID/PW만 받으면 몇 시간 만에 10개 은행 연동 가능
- 유일한 실용 대안: 비마이데이터 사업자가 금융데이터 접근하는 거의 유일한 상용 솔루션
- 국내 1위 인프라, 쿠콘 본사 레거시로 안정성 우수
- 홈택스·세금계산서·4대보험까지 한 번에 커버 (변호사 세무 자동화에 매력적)

**단점 / 리스크**
- **"간접 스크래핑" 성격:** CODEF 내부가 API 기반인지 스크래핑 기반인지 기관마다 다름. 은행 정책 바뀌면 기능 침묵 장애 빈번.
- **법적 회색지대의 바닥:** 규제가 더 조이면 CODEF 자체가 영향받고, 그 위에 얹힌 LAW-CADDY도 같이 흔들림
- **마이데이터 기업이 아니므로 CODEF 경유 호출은 금융위 감독 대상이 아님** → 사고 시 구제 경로 불명확
- **지원 품질 편차:** B2B SaaS 입장에서 티켓 응답속도·SLA가 애매하다는 업계 평
- **비용 예측 어려움:** 볼륨 할인 협상 필요, 초기 계약 단가 협상력 약함

## 4. 법적·규제 리스크 심층 분석 ⚠️

> **이 섹션이 가장 중요. 변호사 대상 SaaS에서 "금융정보 + 법률정보"를 동시에 다루면 사고 1건의 파급이 다른 업종의 10배다.**

### 4.1 핵심 쟁점 5가지

#### 쟁점 ①: SaaS가 고객의 인터넷뱅킹 ID/PW·공동인증서를 "대리 입력"하는 것이 합법인가?

- **법령:** 전자금융거래법 §6 (접근매체의 양도·양수 금지), 신용정보법, 개인정보보호법 §26 (처리 위탁)
- **판례·유권해석:** 명시적 금지는 아니지만, "접근매체 관리 의무 위반"으로 볼 여지가 있음. 2022년 마이데이터 제도 시행 시 **마이데이터 사업자는 스크래핑 전면 금지**되었고, "비(非)마이데이터 기업의 스크래핑"에 대해서는 금융위가 "바람직하지 않다"는 정도의 가이드만 냄 — 즉 불법은 아니나 눈치 보는 구조.
- **LAW-CADDY 포지션:** 변호사 본인 명의 계정을 본인 동의 하에 "위탁 처리"하므로 당장은 합법 해석 가능. 그러나 **사고 발생 시 "변호사가 의뢰인 자금을 관리하는 신탁 계좌까지 노출됐다"는 최악 시나리오**에 휘말릴 수 있음.

#### 쟁점 ②: 스크래핑 방식의 법적 지위 (2022년 이후)

- **2022-01** 금융위원회: 마이데이터 사업자의 스크래핑 전면 금지, API 의무화
- **2025~2026 추세:** 비마이데이터 스크래핑에 대해서도 규제 조임 예상. 금감원 "소비자 보호 강화" 기조로 계속 압박 중
- **실패 사례:** 2022 이전 여러 가계부 앱(뱅크샐러드 포함)이 스크래핑에서 마이데이터 API로 강제 전환. 전환 못한 소형 앱들은 서비스 종료.

#### 쟁점 ③: 마이데이터 라이선스 필요 여부

- **필요한 경우:** "본인 신용정보를 대신 관리·조회해 주는 것을 주된 업(業)"으로 하는 경우 → 본인신용정보관리업 허가 필요 (자본금 5억, 물적요건, 임원 적격성 심사)
- **LAW-CADDY는?** 회계 모듈은 "부수 기능"이며 주된 업은 "법률 문서 자동 생성"이다. **주업이 아니므로 라이선스 요구 대상은 아니다** — 단, 회계 모듈 비중이 커지고 "금융데이터 통합 조회"가 주요 마케팅 문구가 되는 순간 해석 달라질 수 있음.
- **실무적 결론:** 라이선스 필요 없음으로 해석 가능하나, 마케팅 문구에서 "자동 가계부", "모든 계좌 통합 관리" 같은 표현을 써서는 안 됨.

#### 쟁점 ④: 개인정보 처리 위탁 vs 제3자 제공

- **위탁:** 위탁자(변호사) 본인 업무를 위해 수탁자(LAW-CADDY)가 처리 → 사전 동의 불필요, **고지·공개 의무만 충족**하면 됨
- **제3자 제공:** 별도 목적 → 명시적 동의 필수
- **LAW-CADDY 구조:** 변호사가 자기 본인 명의 계좌를 본인 업무(장부 기장)에 쓰기 위해 위임 → **위탁 관계로 구성 가능**. 단, LAW-CADDY → CODEF → 은행 으로 **재위탁이 일어나므로 변호사에게 재위탁 사실을 명시 고지해야 함**.

#### 쟁점 ⑤: 변호사법·변호사윤리장전 특수 이슈

- **변호사법 §26 (비밀유지의무):** 의뢰인 관련 금융정보가 변호사 계좌 거래내역에 찍힘 ("○○○ 착수금 입금"). 이 정보가 LAW-CADDY를 거쳐 CODEF를 거쳐 쿠콘 서버에 저장되는 구조는 **비밀유지의무 재위탁에 해당할 수 있음**.
- **변호사 업무의 공탁금·신탁금 통장:** 일반 사업용 통장과 분리되어야 한다. LAW-CADDY가 "모든 통장 자동 수집"을 유도하면 변호사가 실수로 신탁계좌까지 연결 → 의뢰인 보호 의무 위반 위험.
- **권고:** "사업용 계좌 1개 + 업무용 카드 1장"으로 **명시적으로 제한**하는 UI 가드레일 필요.

### 4.2 LAW-CADDY가 취해야 할 최소 리스크 포지션

1. **"자동 가계부 SaaS"가 아니라 "변호사가 업로드한 거래내역을 AI로 분류해 주는 도구"로 포지셔닝**
2. **이용약관·개인정보처리방침에 CODEF 재위탁 사실 + 범위 명시**
3. **변호사가 연결 가능한 계좌 수에 상한 (예: 사업용 2개까지)**
4. **신탁계좌·예치금 통장 연결 금지 경고 모달**
5. **거래내역은 **평문**이 아닌 사용자별 **AES 암호화**로 Firestore 저장 (현재 미적용)**
6. **정기 보안 점검 체크리스트 (분기별)**
7. **사고 발생 시 고지·신고 프로세스 SOP 작성**

## 5. 사용자 경험 시나리오

### 시나리오 A: 신한은행 개인사업자 통장 연동 첫 설정

**현재 CODEF 방식:**
1. 설정 → 계좌 연동 → 신한은행 선택 → 별칭 입력 → 카카오 인증 시작
2. 카카오톡 푸시 → 사용자 수락 → CODEF 콜백 → `connectedId` 발급
3. **소요 시간: 1~3분** (카카오 인증 지연 시)
4. **흔한 에러:**
   - "간편인증 시간 만료" (120초 내 미수락)
   - "기관 점검 중" (CODEF 기관 상태)
   - "미등록 사용자" (해당 은행에서 카카오 인증 미등록)
   - "비밀번호 5회 오류로 계정 잠김" (공동인증서 폴백 시)

**수기 업로드 방식 (제안):**
1. 신한 홈페이지 → 거래내역 → CSV 다운로드 (사용자 기존 습관)
2. LAW-CADDY → 거래내역 업로드 → 파일 드래그
3. 자동 파싱 → "78건 발견, AI 분류 시작" → 완료
4. **소요 시간: 2~4분** (은행 웹사이트 이동 시간 포함)

**결정:** 소요 시간 차이가 크지 않다. 수기가 오히려 "실패율이 0에 가깝다"는 강점.

### 시나리오 B: 월 1회 동기화 후 거래 50건 검토

**단계:**
1. 변호사가 매월 1일 출근 직후 "이번 달 동기화" 클릭
2. AI가 50건 중:
   - 35건: 자동 매칭 (`confidence >= 0.85`) — 매출/경비 자동 생성
   - 12건: 변호사 확인 대기 (`0.5 <= conf < 0.85`)
   - 3건: 매칭 불가 (신원 불명 입금 등)
3. 대기 화면에서 각 건 옆 [확인] / [수정] / [무시] 버튼
4. 평균 소요: 건당 10초 → 전체 2~3분
5. **품질 목표:** 자동 매칭 정확도 95%+ (1건 오분류 = 장부 1건 손수 수정 부담)

**UI 개선 포인트:**
- 의뢰인 이름이 거래 메모에 포함된 입금은 거의 100% 자동 처리
- "마포 스타벅스 ₩5,800"은 접대비냐 개인소비냐 애매 → 변호사 기본 룰 설정("카페/식당은 모두 업무경비로 가정") 제공 필요
- 일괄 선택 + 일괄 확인 기능 필수 (건별 클릭은 50건에서 피로)

### 시나리오 C: BC카드 사업자 + 삼성카드 개인 2장

**이상:**
- 사업용 BC카드는 전부 경비 후보
- 개인 삼성카드는 원칙적으로 비연결 (개인정보 유입 차단)
- 단, "경조사비·출장비 등 개인카드로 대납 후 정산"은 변호사 수동 입력 지원

**UI 가드레일:**
- 계좌/카드 연결 시 "이 카드는 업무용입니까?" 필수 체크박스
- "개인용" 선택 시 = 연결 자체를 **차단** (개인 지출 유입 금지)
- 접대비/개인 구분은 AI + 사용자 룰(사업자번호 매칭, 특정 가맹점 룰)

## 6. 통합 권장안 — 3가지 옵션

### Option A: CODEF 현행 유지 + 다듬기

**작업 목록 (4~6주):**
1. 백엔드 `/api/codef/*` 프록시 구현·배포 (Firebase Functions 또는 Express)
2. CODEF RSA 공개키 받아 비밀번호 암호화 송신 로직 추가
3. `CodefSyncTab.tsx`를 `bankMatcher`/`cardClassifier` 오케스트레이터 경유로 리팩터
4. 카카오 간편인증 2단계 콜백 폴링 구현
5. Firestore 보안 규칙, 암호화 필드, 민감 로깅 제거
6. 재시도·페이지네이션·스케줄러
7. 이용약관·처리방침 업데이트 (CODEF 재위탁 고지)

**예상 월 운영 비용:** 사용자 100명 기준 50~150만 원 (CODEF) + Firestore/Functions

**리스크:** 회색지대 법적 포지션, CODEF 장애 전파, 변호사 반응 양극화("편하다" vs "불안하다")

**권장도: 5.5/10** — 4~6주 MVP에는 작업 많음, 베타 출시엔 무겁다.

---

### Option B ⭐: 수기 CSV 업로드 + AI 분류 (Phase 2로 CODEF 연기)

**핵심 아이디어:** CODEF 원시 API 호출 레이어만 "파일 업로드 파서"로 교체. `bankMatcher.ts`·`cardClassifier.ts`의 AI 매칭 로직은 **그대로 재사용**.

**작업 목록 (1~2주 스프린트):**
1. `src/services/csvParser.ts` 신규 (은행별·카드사별 포맷 10~15개)
   - 신한/국민/하나/우리/기업/농협 + 인뱅3 은행 거래내역 CSV
   - 삼성/BC/신한/현대/KB 카드 승인내역 CSV
   - PDF 명세서 파싱(선택): Claude Vision 또는 `pdf-parse`
2. `RawBankTransaction` / `RawCardTransaction` 타입으로 정규화 (이미 있는 타입 재사용!)
3. `bankMatcher.runBankSyncAndMatch` 호출부만 CODEF 수집 대신 파싱 결과 주입
4. `CodefSyncTab.tsx`를 `TransactionUploadTab.tsx`로 리네이밍 + 드래그·드롭 UI
5. `codefApi.ts` / `CodefAccountSetup.tsx`를 **삭제하지 않고 `disabled` 플래그로 숨김**
6. 마케팅: "은행 CSV 업로드만 해주세요, AI가 알아서 분류합니다"

**기존 코드 처리:**
- ✅ 유지: `bankMatcher.ts`, `cardClassifier.ts`, `types/codef.ts`, Firestore 스키마, AI 프롬프트, `/api/codef/match-deposits`·`/api/codef/classify-expenses` (AI 부분만)
- 🟡 숨김: `CodefAccountSetup.tsx`, `CodefSyncTab.tsx`의 연결·동기화 버튼 섹션
- 🔴 제거 후보: `connect`·`bank-sync`·`card-sync`·`hometax-sync` 프록시 (나중에 되살릴 수 있게 feature flag)

**월 운영 비용:** **0원** (CODEF 없음)
- Claude API(AI 매칭/분류)만 소요 → 기존 Pro 89k 요금제 원가 안에서 흡수

**법적 리스크:** **거의 0** — 변호사가 자기 손으로 다운받아 업로드. SaaS는 "업로드된 파일을 처리"할 뿐.

**단점:**
- 매월 수동 작업 5분 필요 (자동 아님)
- 변호사 기대치 관리 필요 ("자동 연동은 곧 지원 예정"으로 표시)

**권장도: 8.5/10** — **4~6주 MVP 베타에 최적**

---

### Option C: 오픈뱅킹 정식 + 마이데이터 파트너 (장기)

**구성:**
- 은행 거래내역 → 오픈뱅킹 이용기관 등록 후 정식 API
- 카드 거래내역 → 마이데이터 사업자(예: 뱅크샐러드·토스·핀크) 파트너십 체결 후 화이트라벨 연동
- 홈택스 → CODEF 유지 (공공 API는 합법)

**작업 기간:** 3~6개월 (이용기관 심사 포함)

**비용:** 오픈뱅킹 수수료 + 파트너 리베뉴 셰어

**장점:** 법적 리스크 최저, 규제 당국 친화적, 장기 B2B 영업 시 설득력

**단점:** 4~6주 MVP에는 절대 불가능

**권장도: 8/10 (6개월 후 Phase 3)** — MVP 이후 Series A 전후로 전환 목표

### 8.4 베타 공개 범위

1. **MVP 출시 시점:** 수기 업로드 + AI 매칭/분류 (Option B)
2. **M+2 (베타 1개월 후):** 실제 변호사 5~10명 피드백 수집. "자동 연동 원하시나요?" 설문
3. **M+3 (조건부):** CODEF 프록시 백엔드 완성, **내부 직원 계정 2개에만** 실증 운영
4. **M+6:** 법무 검토(변호사 자문) 통과 후 유료 사용자 중 지원자 한정 오픈
5. **M+12:** 오픈뱅킹 이용기관 등록 진행 (Option C 전환 준비)
